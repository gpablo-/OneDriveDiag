OneDriveDiag - OneDrive Diagnostic Collector

Companion guide for OneDriveDiag.ps1, version 1.0.0. Client agnostic. Read-only. Runs in the user context.

1. Purpose

This tool collects a complete, read-only baseline of OneDrive health on one Windows PC. It is built for cases where a user reports sync problems (red crosses, files that do not sync, stuck folders) and the cause is not obvious. It gives the helpdesk a plain-language summary, and gives L2 the raw evidence in one package.

The tool does not change, reset, repair or unlink OneDrive. Its only writes are inside its own output folder.

Why a single tool. In past cases, early checks looked at the wrong folder (a library mounted outside the OneDrive folder), found a healthy sync engine, and still left the user with visible faults. This tool finds the real sync roots first, reads the engine counters and the binary logs, and indexes the affected tree once, so the next person starts with evidence instead of guesses.

2. Quick start for the helpdesk

  1. Sign in as the user who has the problem, or open a shell in that user's context. Do not use SYSTEM.
  2. Get OneDriveDiag.ps1 onto the PC in C:\temp. Either copy it there, or download the latest version from GitHub by pasting this into Windows PowerShell: 
    if (-not (Test-Path 'C:\Temp')) { New-Item -ItemType Directory -Path 'C:\Temp' | Out-Null }
[Net.ServicePointManager]::SecurityProtocol = [Net.ServicePointManager]::SecurityProtocol -bor [Net.SecurityProtocolType]::Tls12
Remove-Item -LiteralPath 'C:\Temp\OneDriveDiag.ps1' -Force -ErrorAction SilentlyContinue
Invoke-WebRequest -Uri ('https://raw.githubusercontent.com/gpablo-/OneDriveDiag/main/OneDriveDiag.ps1?t=' + [DateTime]::UtcNow.Ticks) -OutFile 'C:\Temp\OneDriveDiag.ps1' -UseBasicParsing
Unblock-File -Path 'C:\Temp\OneDriveDiag.ps1'
Get-Item 'C:\Temp\OneDriveDiag.ps1' | Select-Object FullName, Length, LastWriteTime
    This creates C:\Temp if it is missing, turns on TLS 1.2 (older Windows PowerShell 5.1 builds need it to reach GitHub), removes any older copy (even if it is read-only), downloads the latest script, removes the "downloaded from the internet" block, and shows the file so you can confirm it arrived (about 150 KB). The ?t= value on the link stops a cached older copy being served. Use the raw.githubusercontent.com link, not the github.com/.../blob/... page link, which downloads a web page instead of the script.
  3. Open Windows PowerShell. Run: 
    powershell.exe -ExecutionPolicy Bypass -File C:\temp\OneDriveDiag.ps1
  4. Answer the questions on screen. Press Enter to accept the default (shown as "default"). Standard is the usual choice.
  5. Read the plan, then press Enter to start. Keep the window open. A progress bar shows each step.
  6. When you see Collection complete, open 00_Summary.txt. Attach the zip (or the folder) to the ticket.
  7. Write down the exact path of a file or folder that shows the problem, the time it happened, and take a screenshot with the Status column visible in File Explorer. Add these to the ticket.
Do not reset, unlink or reinstall OneDrive on a large library until L2 has reviewed the package. A rebuild of a library with hundreds of thousands of items can cost the user a full day.

6. Reading the summary

Each check ends with one of four results.

ResultMeaning
FAILA fault that normally stops sync. Fix it or escalate.
WARNA likely contributor. Review it. Escalate if the user still has the problem.
INFOContext for L2. Not a fault on its own.
PASSThe check is healthy.

A result with no FAIL and no WARN does not prove the user has no problem. It means the PC side is healthy. Server-side conditions (for example a SharePoint site storage lock, permissions, or item metadata) cannot be seen from the PC. Compare the exact failing item with SharePoint Online.

8. Large libraries

The file index never walks a large library without asking. The tool reads the item count that OneDrive already reports in SyncDiagnostics (files plus folders). When the count is above -LargeDatasetThreshold (default 100,000) and you have not narrowed the scan, you choose:

  1. Top-level folders only (fast).
  2. Index one folder that you name (best when the problem area is known).
  3. Index everything (stops at the time limit per sync root).
  4. Skip the file index.

In -Unattended mode the default is top-level only. To scan one folder in a very large library:

.\OneDriveDiag.ps1 -Level Standard -Unattended -Zip -SyncRoot 'C:\Users\jsmith\Contoso\Projects - Documents' -FocusPath 'Project A'

How the single pass keeps cost down:

  • One walk per root builds all counts, the exceptions list and the optional full index.
  • Only file attributes, sizes and dates are read. No file is opened or downloaded.
  • Results stream to disk, so memory stays small.
  • Each problem category is capped at -MaxExceptionsPerCategory rows, but totals are always full counts.
  • The full CSV of every item is optional because it is large (about 100 MB per 400,000 items).
  • A time limit stops a long scan cleanly and marks the result partial.
  • Paths longer than 260 characters are read by using the long path prefix.
Reading a folder in a OneDrive library can make OneDrive list that folder from the cloud the first time. This is normal and read-only, but it is the reason a full scan of a very large library is not the default.

11. RMM shell use

  • Use a user context shell, not the system shell. OneDrive data is in the user profile.
  • Add -Unattended. Prompts do not work reliably in many RMM shells. Some RMM shells (for example NinjaOne) do support prompts, in which case the guided run works.
  • Some RMM "run as logged-on user" shells keep the SYSTEM agent's environment variables (for example %OneDrive% pointing at C:\Windows\system32\config\systemprofile). The tool does not trust these. It reads the user's profile, AppData and OneDrive folders from the user's registry, and records an INFO note when the shell environment differs.
  • The tool writes to files and shows only short status lines, so the shell buffer is not flooded. Do not print the contents of ODL files in the shell. Read the signature file instead.
  • Use -Zip so there is one file to collect.
  • Run elevated if you want the filter driver list (fltmc). Everything else works without elevation.

12. Safety and privacy

  • Read-only. The tool does not start, stop, reset or reconfigure OneDrive.
  • It reads registry keys, ini files, event logs, folder metadata and ODL logs. It runs reg export, netsh, fsutil (query only), dsregcmd, sc query, w32tm and fltmc (when elevated).
  • It does not read the content of user files.
  • The package contains the user email, tenant and site names, library URLs, file and folder names, and event log text. Treat it as confidential. Store it only in approved ticket or file storage.

14. Design notes

  • Sync roots come from Windows, not from guessing. The tool reads HKCU:\Software\SyncEngines\Providers\OneDrive and the library table (libraryScope and libraryFolder lines) in the account ini file. It then removes duplicates by local folder.
  • OneDrive ini files are UTF-16 without a byte order mark. Get-Content reads them as garbage on Windows PowerShell 5.1, so every check silently finds nothing. The tool detects the encoding from the bytes and reads every OneDrive text file through one helper.
  • Compressed logs. An .odlgz file is a 256 byte ODL header followed by gzip data. The tool finds the gzip signature and decompresses in memory. .odlsent files are already uploaded and stripped, so they are skipped.
  • No console, no hang. When the input stream is closed (RMM shells), Read-Host returns nothing. The tool treats that as unattended mode for the rest of the run.
  • Portable zip. Entries are written with forward slashes. The built-in folder zip on Windows PowerShell 5.1 writes backslashes, which some unzip tools cannot extract.
  • Healthy counters are evidence. SyncDiagnostics.log counters at zero show the engine is not failing. The tool reports this as a PASS so it can be used to rule the client out.
  • Binary logs are summarised, not dumped. ODL files are read in memory, short readable snippets are cut around error words, ids are replaced by markers, and snippets are counted. Hundreds of thousands of lines become a short list.
  • File state is decoded. Cloud Files uses attribute bits that .NET does not name: online-only (0x400000 and 0x1000), pinned (0x80000), unpinned (0x100000). The tool decodes them.
  • Reparse points are not errors. OneDrive placeholders are reparse points. The tool samples folders that carry no cloud flag and checks their reparse tag, so real junctions and symbolic links are separated from placeholders.
  • Name checks match what SharePoint rejects (leading or trailing spaces, trailing period, reserved names, _vti_, a Forms folder at the library root). The characters # and % are not flagged because current OneDrive accepts them.
  • Server path estimate. Library URL path length plus the path below the sync root. It is an estimate against the 400 character SharePoint limit.
  • No third-party modules. The script uses built-in cmdlets and .NET only. It does not use any custom module.
  • Written for Windows PowerShell 5.1. It also runs in PowerShell 7 on Windows.

15. Limitations

  • The tool sees the PC, not SharePoint Online. It cannot see a site storage lock, permissions, checked-out files or item metadata. Compare a failing item with the web.
  • The tool cannot see which exact items show a red cross in File Explorer. Ask the user for a screenshot and a full path. The exceptions CSV narrows the list.
  • ODL log text differs between OneDrive versions. Some versions hold little readable text.
  • Elevation is needed for the filter driver list. Reparse tag sampling uses fsutil and may be unavailable without elevation.
  • Event log names differ on some builds. Missing logs are skipped quietly.
  • Version 1.0.0 was tested on Windows 11 with Windows PowerShell 5.1 and PowerShell 7 (Quick, Standard and Deep, interactive fallback, unattended, large library guard, focus folder, zip and zip only), not elevated, on a PC with a work and a personal account. Elevated checks (fltmc, fsutil reparse sampling) and the SYSTEM and user mismatch paths still need field testing. Report any "Step stopped early" finding.
